# Loft

Open-source (MIT), self-hostable, browser-based parametric 3D CAD. Python
FastAPI services on the OCCT kernel; React + three.js front end.

**Every decision answers one question: would a working engineer model a real
part in this today?** Where Fusion 360, SolidWorks or Onshape have an
established way to do something, do it that way unless `docs/VISION.md` or the
founder says otherwise.

The orchestrator (main session) also reads `.claude/ORCHESTRATOR.md`.

## Layout

```
apps/web            React 19 + Vite SPA, react-three-fiber viewport
services/gateway    auth, REST aggregation, proxy to the other services
services/geometry   OCCT via OCP/build123d: features, tessellation, export
services/documents  parts, assemblies, drawings, feature trees (Postgres)
packages/loft-wire  pydantic wire types      packages/py-kit  shared service kit
packages/loft-script  public Python API      packages/design  tokens + UI primitives
packages/contracts, packages/ts-client       generated by `just gen`, never hand-edited
docs/               VISION, ROADMAP, BACKLOG, RESEARCH (architecture decisions),
                    ENVIRONMENT (sandbox quirks: read before booting a stack)
```

## Commands

```bash
just lint     # ruff, pyright, eslint/prettier, tsc, licence + repo checks
just test     # pytest + vitest
just gen      # regenerate contracts + ts-client (+ `just gen-verify` before committing)
just e2e      # geometry goldens + Playwright; boots its own stack
scripts/e2e.sh --web-only -- e2e/<spec>.ts   # one spec
```

## Invariants

- Work on the current `claude/*` branch. Never push to `main` without the
  founder. Never push a red build.
- Types flow one way: pydantic -> `just gen` -> contracts -> ts-client. No
  hand-written copies of API types.
- Only `services/geometry` imports OCP/build123d. Geometry never touches
  Postgres, documents never imports the kernel, and the web app talks only to
  the gateway.
- No GPL/AGPL dependencies (LGPL, dynamically linked, is fine).
- Schema changes go through alembic migrations.
- A new modelling capability ships with a golden model
  (`services/geometry/goldens/`). Never loosen a golden tolerance to go green.
  Rebuilds are deterministic.

## Severity: what gets fixed now

**Blocking** means data loss or corruption, wrong geometry a user would see or
export, a crash or hang, or a security hole. Fix it before merging.

Anything else becomes one line under "Notes" in `docs/BACKLOG.md` (or in the
commit message), not a task. The founder triages the notes weekly, and most
are closed without work. Each change gets one review. Review again only if a
blocking fix was made.

## Gates, in proportion to risk

- Kernel geometry and anything that stores user data get the strict gates:
  goldens, STEP round-trip, determinism, and migrations tested.
- Everything else: typecheck, unit tests, and the e2e specs that cover the
  change. Take screenshots only for real visual changes.
- CI on the pushed commit is the final gate. Subagents cannot reach
  api.github.com: push, report the SHA, and the orchestrator reads CI.

## Git

- Worktrees are created from an old commit. Before reading code, run
  `git fetch origin <branch> && git reset --hard origin/<branch>`, then
  `pnpm install --frozen-lockfile`.
- Push by value: `git push origin HEAD:<branch>`, then confirm that
  `git ls-remote origin <branch>` equals `HEAD`. From a worktree,
  `git push -u origin <branch>` pushes the wrong ref and still says
  "up-to-date". If the push is rejected, `git pull --rebase` and re-run your
  gates.
- Never run `git stash` (the stash is shared across worktrees) and never run
  `git add -A`. Stage the paths by name.
- Use conventional commits, one logical change per commit.

## Reports

At most 15 lines: what changed, the evidence (commands and counts), and
anything the founder must decide. Put findings you did not fix in one line
each.
